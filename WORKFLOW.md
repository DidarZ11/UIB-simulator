# Как работаем вместе

Правила для всех троих. Цель одна: чтобы никто никому не мешал и рабочая версия проекта не ломалась.

Описание проекта: [PROJECT.md](PROJECT.md). План месяца: [PLAN-MONTH-1.md](PLAN-MONTH-1.md).

## 1. Главная идея за две минуты

- **Репозиторий** — общая папка проекта на GitHub: https://github.com/DidarZ11/UIB-simulator
- **`main`** — главная ветка, рабочая версия проекта. Она должна запускаться всегда. **Напрямую в `main` не пишет никто.**
- **Ветка** — твоя личная копия проекта. В ней можно править что угодно, остальных это не трогает.
- **Коммит** — сохранённый шаг в ветке, с подписью, что сделано.
- **Пул-реквест (PR)** — заявка на сайте GitHub: «добавьте мою ветку в `main`». Другой человек смотрит и нажимает Merge.

Вся работа — это круг: **взял свежий `main` → сделал свою ветку → поработал → отправил PR → его приняли → снова взял свежий `main`.**

## 2. Один раз: подготовка компьютера

Нужны: Git, Node.js (версия 20 или новее), редактор (VS Code).

```bash
git clone https://github.com/DidarZ11/UIB-simulator.git
cd UIB-simulator/web
npm install
npm run dev
```

После этого игра открывается на http://localhost:3000.

Представиться git (один раз на компьютере):

```bash
git config --global user.name "Твоё Имя"
git config --global user.email "твоя@почта.com"
```

Используй ту же почту, что в аккаунте GitHub: тогда коммиты подписываются твоим аккаунтом.

## 3. Кто за какие файлы отвечает

Чтобы не править один и тот же файл одновременно, у каждой зоны своя папка.

| Зона | Папки | Что там |
|---|---|---|
| **Моделирование** | `blender/`, `web/public/models/`, `web/src/game/`, `web/src/data/floors/` | 3D-сцена, JSON этажей, мебель, персонаж, камера |
| **Панели** | `web/src/app/` (кроме общих файлов) | Страницы сайта: вход, панели студента, преподавателя, админа |
| **Бэкенд** | `web/src/server/`, `supabase/` (создаёт бэкендер) | База, вход, роли, хранение файлов, адаптер Academo |

**Правила зон**
1. Свою папку правишь сам, без вопросов.
2. В чужую папку не лезешь. Если нужно поправить, напиши владельцу и объясни зачем. Он сделает сам или разрешит тебе.
3. Новый тип файлов или новую папку сначала обсуди в чате, потом создавай.

**Общие файлы** (правит тот, кому нужно, но **предупреди в чате**): `web/package.json`, `web/package-lock.json`, `web/tsconfig.json`, `web/next.config.ts`, `PROJECT.md`, этот файл.

## 4. Ежедневный круг работы

### Шаг 1. Начало работы: свежий `main`

```bash
git switch main
git pull
```

Делай это **перед каждой новой задачей**. Если пропустить, ты начнёшь со старой версии и потом получишь конфликты.

### Шаг 2. Своя ветка

```bash
git switch -c зона/что-делаю
```

Примеры имён: `model/chair`, `model/room-numbers`, `panels/login`, `backend/tables`. Одна ветка — одна задача. Не складывай в одну ветку несколько несвязанных дел.

### Шаг 3. Работа и коммиты

Работай как обычно. Когда закончил небольшой законченный кусок:

```bash
git status            # посмотреть, что изменилось
git add .             # отобрать все изменения
git commit -m "Коротко, что сделано"
```

Хорошая подпись: «Добавил стул и доску в Blender». Плохая: «правки», «fix», «123».

Коммить часто, минимум в конце каждого рабочего дня. Так нет риска потерять работу.

### Шаг 4. Отправить ветку на GitHub

В первый раз для этой ветки:

```bash
git push -u origin имя-ветки
```

Дальше достаточно `git push`.

### Шаг 5. Пул-реквест

1. Открой репозиторий на GitHub. Там появится жёлтая плашка **Compare & pull request**, нажми её.
2. Заголовок: что сделано одной строкой.
3. В описании: что изменил, как проверить. Если меняются картинки или 3D, приложи скриншот.
4. Справа в Reviewers выбери одного из команды.
5. Нажми **Create pull request**.

### Шаг 6. Проверка и слияние

- Тот, кого ты выбрал, открывает PR, смотрит файлы (вкладка Files changed) и, если нужно, запускает ветку у себя (раздел 6).
- Если всё хорошо: **Approve**, затем **Merge pull request**.
- Если есть замечания: пишет комментарии. Ты правишь в той же ветке, коммитишь, пушишь, PR обновится сам.
- **Свой PR сам не сливаешь**, пока другой не посмотрел. Исключение: мелочь вроде исправления опечатки в документе.

После слияния возвращайся к шагу 1.

## 5. Что нельзя делать

1. **Писать прямо в `main`.** Всегда через ветку и PR.
2. **Принудительный пуш:** `git push --force`. Это стирает чужие изменения.
3. **Коммитить секреты.** Ключи Supabase, пароли, токены, файлы `.env` не попадают в репозиторий. Они уже в `.gitignore`. Значения ключей передаём друг другу через личные сообщения.
4. **Коммитить фото людей.** Папка `Фото холл/` в игноре, фото хранятся на общем Google Drive.
5. **Коммитить `node_modules/` и `.next/`.** Они в игноре, если не трогать `.gitignore`.
6. **Сливать PR, который не запускается.** Если проект после твоей ветки не стартует, это не готово.
7. **Править один и тот же файл параллельно с другим человеком.** Если очень нужно, скажи ему в чате.

## 6. Как проверить чужую ветку у себя

```bash
git fetch
git switch имя-чужой-ветки
cd web
npm install
npm run dev
```

Посмотри в браузере. Потом вернись: `git switch main`.

## 7. Если что-то пошло не так

### Конфликт при слиянии

Конфликт бывает, когда два человека поменяли одну и ту же строку. Git не понимает, какая версия правильная.

Признак: GitHub пишет на PR «This branch has conflicts», или git пишет `CONFLICT` при `git pull` или `git merge`.

Что делать:
1. Не паникуй, ничего не потеряно.
2. Обнови свою ветку главной: `git switch твоя-ветка`, затем `git merge main`.
3. Открой файлы с пометками `<<<<<<<`, `=======`, `>>>>>>>`. Между ними две версии. Оставь нужную (или объедини), а строки с `<<<<<<<` и `>>>>>>>` удали.
4. `git add .`, затем `git commit`, затем `git push`.

Если запутался, **остановись и напиши в чат**, не пытайся «чинить» наугад. С конфликтами можно разобраться вместе.

### Сделал изменения не в той ветке

```bash
git stash                      # спрятать изменения
git switch нужная-ветка
git stash pop                  # вернуть изменения здесь
```

### Случайно закоммитил лишнее в своей ветке (до пуша)

```bash
git reset --soft HEAD~1        # отменить последний коммит, изменения остаются
```

### После слияния чужой ветки проект не запускается

Почти всегда помогает:

```bash
git switch main
git pull
cd web
npm install
npm run dev
```

Причина: в чужой ветке могли добавиться библиотеки, а у тебя их нет.

### Удалил или испортил что-то в файлах, а коммита не было

`git restore путь/к/файлу` вернёт файл, как в последнем коммите. Внимание: несохранённые правки в этом файле пропадут.

## 8. Особые правила

### Файлы Blender (`.blend`)

- `.blend` бинарный: Git не умеет сливать два его разных изменения.
- Поэтому **`blender/` правит только отвечающий за моделирование**. Остальные берут готовые `.glb` из `web/public/models/`.
- Перед тем как начать править `.blend`, убедись, что у тебя свежий `main`.
- Экспорт GLB и `.blend` коммитим вместе, чтобы они не расходились.

### Библиотеки (`package.json`)

- Новую библиотеку ставит тот, кому она нужна, командой `npm install название`. Изменятся `package.json` и `package-lock.json`.
- **Предупреди остальных в чате**, когда сливаешь такой PR. Им после `git pull` нужно выполнить `npm install`.
- Не ставь «на всякий случай». Каждая библиотека — это вес и риск.

### Тексты интерфейса

- Все тексты лежат в `web/src/i18n/` (русский, потом казахский и английский). Не пиши русские строки прямо в компонентах, добавляй их в файл переводов.
- Файл переводов общий. Пул-реквесты с ним делай небольшими и сливай быстро, чтобы не было конфликтов.

### Данные этажей

- JSON этажей (`web/src/data/floors/`) правит только моделирование. Если панелям нужно знать номера кабинетов, читают этот JSON, а не копируют его.

## 9. Где зоны пересекаются (договоритесь заранее)

Три задачи четвёртой недели плана сходятся в одну: вход в кабинет открывает задания его дисциплины.

| Задача | Кто |
|---|---|
| Кабинет с номером в JSON и событие «игрок вошёл в кабинет N» | Моделирование |
| Привязка дисциплины к кабинету в базе | Бэкенд |
| Окно задания поверх 3D и кнопка «телепорт в кабинет» | Панели |

**Договорённость, которую нужно записать здесь к концу октября:**
- Как кабинет получает свой `id` (например, `"room-101"`).
- Как игра сообщает панелям «вошёл в кабинет `room-101`» (функция или событие).
- Как панели просят игру «телепортируй в `room-101`».

До записи договорённости каждый работает в своей зоне и эти места не трогает.

## 10. Памятка: всё на одном экране

```bash
# начало задачи
git switch main
git pull
git switch -c зона/что-делаю

# в процессе
git status
git add .
git commit -m "Что сделано"

# отправить
git push -u origin имя-ветки
# на GitHub: Compare & pull request → выбрать проверяющего → Create

# после слияния
git switch main
git pull
```

**Золотые правила:**
1. В `main` напрямую не пишем.
2. Перед новой задачей: `git pull` на `main`.
3. Одна ветка — одна задача.
4. Коммитим часто, подписываем понятно.
5. Чужие папки не трогаем без разговора.
6. Секреты и фото людей в репозиторий не кладём.
7. Не знаешь, что делать: напиши в чат, не чини наугад.

## 11. Настройка репозитория (один раз, делает владелец)

На GitHub: **Settings → Branches → Add branch ruleset** для ветки `main`:
- Require a pull request before merging (нужен PR).
- Require approvals: 1 (нужна одна проверка).
- Block force pushes (запрет принудительного пуша).

**Settings → Collaborators**: добавить двух остальных участников команды.
